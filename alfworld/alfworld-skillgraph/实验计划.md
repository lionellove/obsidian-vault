# Skill Package 自进化研究计划

## 1. 出发点

最开始的想法是把自然语言 `SKILL.md` 转成 SkillGraph，用显式的 node、edge、condition、verification、fallback 来减少模型在执行过程中的自由推理。

但继续看 HiSkill、SkillGraph、SkillSmith 等工作之后，单纯研究：

> graph 是否优于 flat skill

已经不太够了。

HiSkill 已经说明了：

- procedure 拆成 atomic operation 有帮助；
    
- typed edge 有帮助；
    
- state-aware execution 有帮助；
    
- support / recovery 有帮助；
    
- runtime 只取相关 subgraph 可以减少 token；
    
- 单纯把 Top-K skill text 塞给模型不如显式的 procedural structure。
    

因此后续不应该继续把重点放在“设计一种新的 graph”。

更值得研究的问题变成：

> **一个 skill 中到底什么信息需要被显式化？这些信息应该被显式化成什么形式？**

这里也不能默认所有内容都应该进入 workflow。

一个实际的 skill 可能同时包含：

```text
Skill Package
│
├── Workflow
│   ├── Node
│   └── Edge
│
├── Constraint
│
├── Verification
│
├── Fallback / Recovery
│
└── 后续可扩展
    ├── Reference
    ├── Boundary
    └── Tool Contract
```

因此：

[  
SkillGraph \subset SkillPackage  
]

Graph 只是 Skill Package 中负责 procedural control flow 的一部分。

---

# 2. 核心问题

目前最想回答的问题可以概括成：

> **Agent 在执行任务、暴露错误以后，能不能根据 execution feedback 自动判断当前 skill 缺少什么语义，并把这部分语义以合适的形式加入 Skill Package？**

这里的重点不是：

```text
失败
→ 增加一个 node
```

而是：

```text
失败
→ 判断缺了什么
→ 判断应该表示成什么
→ 对 Skill Package 做最小修改
```

例如同一个 failure insight：

> 搜索证据不足时，agent 不应该直接回答。

它可能被表示成：

### Workflow

```text
search
  ↓
check evidence
  ├─ sufficient → answer
  └─ insufficient → reformulate → search
```

### Constraint

```text
Do not answer when evidence is insufficient.
```

### Verification

```text
Before finalizing, verify that sufficient evidence has been collected.
```

### Fallback

```text
insufficient evidence
→ reformulate query
→ retry search
```

因此真正需要研究的是：

[  
\boxed{  
Failure\ experience  
\rightarrow  
Appropriate\ explicit\ representation  
}  
]

---

# 3. 需要证明什么

## 3.1 需要证明 Patch 比自由重写 Skill 更合适

最基础的问题是：

> 为什么不让 LLM 每次失败后直接重新写一份 `SKILL.md`？

需要验证结构化 Patch 是否有这些优势：

- 修改范围更小；
    
- 更容易验证；
    
- 更容易知道具体改了什么；
    
- 更少破坏已有正确行为；
    
- skill 不容易越来越冗长；
    
- runtime token 增长更可控；
    
- evolution 过程可以被审计和回滚。
    

可以比较：

```text
No evolution
vs
Free skill rewrite
vs
Structured Patch
```

---

## 3.2 需要证明不同类型的显式信息确实有不同作用

不能一开始就假设：

```text
Node + Edge + Constraint + Verification + Fallback
```

一定是最优表示。

需要做 ablation，例如：

|方法|可修改内容|
|---|---|
|Rule-only|Constraint|
|Graph-only|Node + Edge|
|Graph + Verification|Node + Edge + Verification|
|Full Patch|Node + Edge + Constraint + Verification + Fallback|
|Free Rewrite|无结构限制|

观察不同类型的信息在什么任务中有效。

最后希望回答：

> 哪些 execution semantics 值得显式化，哪些保留成普通文本反而更好？

---

## 3.3 需要证明 Skill 的进化不是 task-specific memorization

这是整个方法比较大的风险。

如果：

```text
task_i
→ failure
→ patch_i
```

每一道题都直接产生永久修改，那么最终 Skill 很容易变成一个错题本：

```text
如果遇到 microwave 1 就……
如果遇到 apple 2 就……
如果来到 kitchen 3 就……
```

这并不是 reusable skill。

所以需要证明：

> Patch 抽取的是 task-level / task-family-level reusable semantics，而不是 instance-specific solution。

这要求 evolution 和 evaluation 分开。

---

## 3.4 需要证明 multi-edit semantic patch 比单 primitive edit 更合理

最开始可以设想：

[  
每轮只增加一个 node  
]

但会产生两个问题。

第一，进化速度很慢。

第二，有些修改天然不能只靠一个 primitive operation 完成。

例如增加一个新 workflow step：

```text
ADD_NODE
```

如果没有对应的：

```text
ADD_EDGE
```

这个节点可能根本不可达。

所以需要区分：

### Primitive Edit

```text
ADD_NODE
ADD_EDGE
ADD_CONSTRAINT
...
```

### Semantic Patch

一个 root cause 对应的一组最小完整修改：

```text
ADD_NODE
+
ADD_EDGE
+
ADD_VERIFICATION
```

三者都在解决：

```text
missing evidence sufficiency handling
```

后续可以比较：

```text
Atomic Semantic Edit
vs
Multi-edit Semantic Patch
```

看：

- 收敛速度；
    
- 最终成功率；
    
- patch 数量；
    
- skill complexity；
    
- regression。
    

---

# 4. 三个需要正式定义的 IR

整个方法不能直接写成：

```text
trajectory
→ reflection
→ new skill
```

这样太黑箱。

更合理的是拆成三个显式中间表示。

---

## 4.1 Skill Package IR

定义当前 skill：

[  
S=(V,E,C,Q,F)  
]

其中：

- (V)：workflow nodes；
    
- (E)：control-flow edges；
    
- (C)：constraints；
    
- (Q)：verifications；
    
- (F)：fallback / recovery。
    

Workflow graph：

[  
G=(V,E)  
]

因此 Skill Package 不等于 Graph：

[  
G\subset S  
]

第一版可以保持结构尽量简单。

### Node

[  
v=(id,type,instruction)  
]

### Edge

[  
e=(source,target,condition)  
]

### Constraint

[  
c=(scope,rule)  
]

### Verification

[  
q=(target,criterion,on_failure)  
]

### Fallback

[  
f=(trigger,target)  
]

后续如果实验需要，再增加 reference、boundary、inputs/outputs 等字段。

---

# 5. Failure IR

Agent 使用当前 Skill：

[  
\tau_i\sim\pi_\theta(x_i,S_t)  
]

其中：

[  
\tau_i=(o_0,a_0,o_1,a_1,\ldots,o_T)  
]

如果任务失败，不直接生成 Patch，而是首先产生：

[  
z_i=A(\tau_i,S_t)  
]

其中 Failure IR 可以定义成：

[  
z_i=  
(type,location,observation,expectation,cause,scope)  
]

例如：

```yaml
type: missing_verification

location: heat_object

observation:
  agent placed the object immediately after heating

expectation:
  object state should be checked before placement

cause:
  current skill does not verify whether heating succeeded

scope:
  heat_and_place
```

这里最重要的是：

> Failure IR 描述的是当前 skill 缺失的语义，而不仅是“agent 做错了什么”。

---

# 6. Root Cause Merge

不能：

```text
一个 trace
→ 一个 patch
```

应该：

```text
多个 trace
→ 多个 Failure IR
→ 合并
→ type-level root causes
```

设一批任务得到：

[  
Z_t={z_1,z_2,\ldots,z_n}  
]

然后：

[  
R_t=M(Z_t)  
]

例如：

```text
Failure 1:
microwave closed before insertion

Failure 2:
cabinet closed before placement

Failure 3:
fridge closed before insertion
```

不能总结成：

```text
Remember to open microwave, cabinet and fridge.
```

而应该抽象成：

```text
Root cause:
The skill lacks a prerequisite check for
receptacle accessibility before insertion.
```

每个 root cause 应保留：

```yaml
root_cause:
  receptacle accessibility is not checked

scope:
  object-placement tasks

supported_by:
  - trace_03
  - trace_11
  - trace_24
```

其中 `supported_by` 很重要。

它能防止一个偶然失败直接污染整个 Skill。

---

# 7. Patch IR

Patch 定义为：

[  
\Delta=  
(\Delta_V,\Delta_E,\Delta_C,\Delta_Q,\Delta_F)  
]

每个部分允许为空：

[  
\Delta_X=\varnothing  
]

也允许：

[  
op\in{ADD,UPDATE,DELETE}  
]

因此一个 Patch 可以是：

```yaml
nodes:
  - op: ADD
    id: check_accessibility
    instruction: Check whether the receptacle is accessible.

edges:
  - op: ADD
    source: locate_receptacle
    target: check_accessibility

constraints: []

verifications:
  - op: ADD
    target: insert_object
    criterion: receptacle is accessible

fallbacks: []
```

完整 Patch 最好和 root cause 绑定：

[  
p=(r,\Delta)  
]

即：

```text
一个 semantic defect
        ↓
一个 semantic patch
        ↓
若干 primitive edits
```

而不是让 LLM 任意修改 Skill。

---

# 8. Scope 需要成为重要字段

Patch 最大的问题之一是过拟合，因此每条 edit 最好具有 scope。

第一版可以先定义：

```text
global
task_family
workflow
local
instance
```

例如：

```text
Never produce an inadmissible action.
```

可能属于：

```text
global
```

而：

```text
Verify heating before placement.
```

可能属于：

```text
heat_and_place
```

而：

```text
Open microwave 1 before inserting apple 2.
```

属于：

```text
instance
```

第一版甚至可以直接规定：

> `instance` scope 的 candidate patch 不允许 commit 到正式 Skill Package。

后续再研究是否可以把 instance patch 抽象成更高层语义。

---

# 9. 整体 Evolution 流程

整个系统可以定义成：

[  
S_0\rightarrow S_1\rightarrow\cdots\rightarrow S_T  
]

每一轮：

## Step 1：执行当前 Skill

从 evolution batch：

[  
B_t={x_1,\ldots,x_k}  
]

运行：

[  
\tau_i\sim\pi_\theta(x_i,S_t)  
]

得到 success / failure trajectories。

---

## Step 2：逐条分析 Failure

对于失败 trajectory：

[  
z_i=A(\tau_i,S_t)  
]

产生 Failure IR。

这一阶段可以由 LLM 完成。

但输出必须受到 schema 约束。

---

## Step 3：合并 Failure

[  
R_t=M({z_i})  
]

Merger 不只是摘要，而是：

```text
clustering
+
abstraction
+
scope estimation
```

目标是发现 recurring / reusable root cause。

---

## Step 4：生成 Candidate Patch

[  
\Delta_t=G(R_t,S_t)  
]

LLM 不能自由重写整个 Skill，而只能使用规定的 Patch DSL：

```text
ADD
UPDATE
DELETE
```

作用于：

```text
NODE
EDGE
CONSTRAINT
VERIFICATION
FALLBACK
```

---

# 10. Hybrid Verifier

Verifier 不应该只有一个。

需要明确拆成三层。

---

## 10.1 Deterministic Verifier

回答：

> 这个 Patch 能不能合法地应用？

例如检查：

- schema 是否正确；
    
- node ID 是否重复；
    
- edge source / target 是否存在；
    
- 删除 node 是否留下 dangling edge；
    
- entry 是否可达；
    
- 是否存在 unreachable node；
    
- verification target 是否存在；
    
- fallback target 是否存在；
    
- retry / cycle 是否非法。
    

定义：

[  
V_{str}(S_t,\Delta_t)\in{0,1}  
]

这些问题应该尽量确定性处理。

---

## 10.2 LLM Semantic Verifier

回答：

> 这个 Patch 是否语义上合理？

例如：

- patch 是否真的解决 root cause；
    
- 是否和已有节点语义重复；
    
- 是否与已有 constraint 冲突；
    
- 是否过于 task-specific；
    
- 是否进行了过度修改；
    
- scope 是否合理。
    

可以输出：

```text
relevance
generality
redundancy
contradiction
over-specificity
```

例如：

[  
V_{sem}(S_t,r_t,\Delta_t)  
\rightarrow  
[0,1]^k  
]

这一阶段更适合 LLM。

---

## 10.3 Dynamic Validation

即使：

```text
Structural verifier: PASS
Semantic verifier: PASS
```

也不能说明 Patch 真有用。

最终还需要：

```text
S_t
vs
Apply(S_t, Δ_t)
```

在 held-out validation batch 上重新运行。

定义：

# [  
J(S,D)

\frac{1}{|D|}  
\sum_{x\in D}  
Eval(\pi_\theta(x,S))  
]

Patch gain：

# [  
Gain(\Delta_t)

## J(Apply(S_t,\Delta_t),D_{val})

J(S_t,D_{val})  
]

只有达到 acceptance criterion：

[  
Gain(\Delta_t)>\epsilon  
]

才真正：

[  
S_{t+1}=Apply(S_t,\Delta_t)  
]

否则：

[  
S_{t+1}=S_t  
]

因此三种 verifier 的位置分别是：

|阶段|回答什么|
|---|---|
|Deterministic|合法吗|
|LLM Semantic|合理吗|
|Dynamic Validation|有效吗|

---

# 11. 为什么不是一个任务一个任务直接更新

如果：

```text
Task 1
→ failure
→ patch
→ commit

Task 2
→ failure
→ patch
→ commit
```

很容易导致：

# [  
Skill

\text{collection of task-specific fixes}  
]

因此更合理的是 mini-batch evolution：

```text
一批任务
↓
收集 traces
↓
逐个分析
↓
合并 recurring failure
↓
candidate patch
↓
验证
↓
commit / reject
```

可以规定每轮任务中尽量覆盖多个 task family。

这样 Patch 的目标是修复：

> distribution-level recurring defect

而不是：

> 当前题目的错误。

---

# 12. 第一阶段为什么使用 ALFWorld

第一阶段不建议直接继续使用 AutomationBench。

Patch evolution 需要大量：

```text
rollout
→ analysis
→ patch
→ rerun
```

AutomationBench 单任务成本比较高，而且失败来源比较复杂：

- tool error；
    
- web / environment；
    
- reasoning；
    
- skill；
    
- format；
    
- external state。
    

不利于首先验证机制。

ALFWorld 更适合作为第一阶段。

原因：

- task 相对短；
    
- action space 比较稳定；
    
- environment state 明确；
    
- failure 原因容易分析；
    
- procedure dependency 明显；
    
- 可以大量反复 rollout；
    
- 有 seen / unseen split。
    

因此可以先验证：

> Patch 机制本身能不能工作。

---

# 13. ALFWorld 数据使用方式

不要：

```text
valid_seen
→ evolution

valid_unseen
→ test
```

更干净的方式是：

```text
ALFWorld train
│
├── evolution subset
│
└── patch-validation subset

============================
freeze final Skill Package
============================

valid_seen
valid_unseen
```

即：

[  
D_{evolve},D_{patch-val}\subset D_{train}  
]

经过 (T) 轮：

[  
S_0\rightarrow\cdots\rightarrow S_T  
]

冻结：

[  
S^*=S_T  
]

然后分别测试：

[  
Perf_{seen}(S^*)  
]

和：

[  
Perf_{unseen}(S^*)  
]

---

# 14. Seen / Unseen 分别证明什么

### valid_seen

主要看：

> 在相似 environment distribution 中，skill 是否能泛化到其他实例。

### valid_unseen

更重要。

主要看：

> skill 学到的是 reusable procedure，还是记住了训练场景。

例如：

```text
Baseline
seen   50
unseen 35

Evolved
seen   75
unseen 38
```

说明很可能产生了明显过拟合。

如果：

```text
Baseline
seen   50
unseen 35

Evolved
seen   70
unseen 62
```

才更支持：

> skill evolution 学到了能够迁移的 execution semantics。

---

# 15. 还需要按 task family 报告结果

仅仅看 seen / unseen 不够。

因为 ALFWorld 的 seen / unseen 主要区分 environment，而不是 task type。

所以最好报告：

|Task type|Seen|Unseen|
|---|--:|--:|
|Pick & Place|||
|Examine|||
|Clean & Place|||
|Heat & Place|||
|Cool & Place|||
|Pick Two & Place|||

这样可以区分：

### 只提升 evolution 中大量出现的 task family

说明：

```text
task-family overfitting
```

### 多个 family 提升，但 unseen 不提升

说明：

```text
environment overfitting
```

### 多个 family、unseen 都提升

才比较支持：

```text
reusable skill learning
```

# 18. 整个方法最终可以形式化成

固定模型：

[  
\pi_\theta  
]

不更新 LLM 参数。

每轮：

[  
\begin{aligned}  
\tau_i &\sim \pi_\theta(x_i,S_t)\  
z_i &= A(\tau_i,S_t)\  
R_t &= M({z_i})\  
\Delta_t &= G(R_t,S_t)\  
\hat S_{t+1} &= Apply(S_t,\Delta_t)  
\end{aligned}  
]

然后验证：

[  
S_{t+1}=  
\begin{cases}  
\hat S_{t+1}, & \text{if patch accepted}\  
S_t, & \text{otherwise}  
\end{cases}  
]

重复：

[  
S_0  
\rightarrow  
S_1  
\rightarrow  
\cdots  
\rightarrow  
S_T  
]

最终目标不应该只是最大化 task performance，因为 skill 无限增长也可以帮助任务。

可以考虑：

# [  
S^*

\arg\max_S  
\left[  
J(S,\mathcal D)  
-\lambda Complexity(S)  
-\mu TokenCost(S)  
\right]  
]

也就是同时考虑：

- performance；
    
- skill complexity；
    
- runtime token cost。

# 19. 目前最需要先完成的工作

现在还不需要马上搭完整系统。

第一步应该先把几个接口定义清楚：

```text
Skill Package IR
Failure IR
Patch IR
```

然后定义：

```text
Failure Analyzer
Root Cause Merger
Patch Generator
Structural Verifier
Semantic Verifier
Patch Validator
```

接口确定后，再逐个实现。

比较合理的开发顺序是：

```text
1. 定义 Skill Package Schema
2. 定义 Patch DSL
3. 实现 Apply(Patch)
4. 实现 deterministic verifier
5. 做人工 Patch，确认整个闭环能跑
6. 实现 trajectory → Failure IR
7. 实现 Failure merge
8. 实现 root cause → Patch
9. 加 semantic verifier
10. 最后接完整 evolution loop
```

其中第 5 步很重要。

应该先证明：

> **如果给一个正确 Patch，Skill Package 的修改和 runtime 确实能按照预期工作。**

不要一开始就同时调：

```text
failure analysis
+
merge
+
patch generation
+
verifier
+
runtime
```

否则最后失败时很难知道是哪一层出了问题。

# 20. 当前研究主线

目前可以把整个方向概括成：

> 已有工作已经说明 procedural graph 对 Agent Skill 有价值，因此后续不再主要研究“Graph 是否有用”，而研究 Agent 在执行反馈下应该将哪些经验显式固化到 Skill 中，以及应该以 workflow、constraint、verification、fallback 等什么形式固化。为此，引入结构化 Failure IR 和 Patch IR，在保持 LLM 参数固定的情况下，通过 execution–diagnosis–patch–validation 的闭环逐步进化外部 Skill Package，并研究这种结构化进化是否能够获得比自由文本 Skill rewrite 更稳定、更可迁移、复杂度更低的 reusable skills。

最核心的一条链就是：

[  
\boxed{  
Trajectory  
\rightarrow  
FailureIR  
\rightarrow  
RootCause  
\rightarrow  
PatchIR  
\rightarrow  
SkillPackageIR  
\rightarrow  
Validation  
}  
]

现在的重点已经不是继续把 SkillGraph 画得更复杂，而是搞清楚：

[  
\boxed{  
\text{What should a skill make explicit, and how should it evolve?}  
}  
]
